### T6.3 - Asset library notes and assumptions
- **Backend lineage extension:** The drawer needs the source job's prompt/model/params and the job inputs, but GET /v1/assets/{id} only returned IDs plus asset metadata. Added an additive lineage block to AssetResponse (source job summary, input asset refs with signed URLs, parent asset). List responses leave lineage null to keep payloads small. OpenAPI spec and packages/api-client were regenerated.
- **Signed URL expiry:** Supabase signed URLs are refreshed by refetching the asset/list once when media fires an error event (there is no HTTP 403 observable from an <img>/<video> load), guarded per asset so a permanently broken file cannot loop.
- **Playwright harness:** The upload E2E runs against a self-contained mock backend (pps/web/e2e/mock-backend.mjs) that also impersonates the Supabase auth /auth/v1/user endpoint, so no Supabase/Redis/API stack is required. Session state is injected as a sb-<ref>-auth-token cookie matching @supabase/ssr's base64url encoding.
- **Design references:** The Stitch screens are light-mode "Luminous Canvas"; the app already ships a dark theme from T6.1/T6.2, so layout/interaction patterns were borrowed (drawer sections, prompt block, lineage tiles) while keeping the existing dark palette.

### T6.4 — Generation composer notes and assumptions
- **Flow mapping:** The five product flows collapse onto four API task types. Image+Text→Video is `image_to_video` with an optional prompt, so the composer exposes Mode (Image/Video) + Starting point (Text only / Text + image) and derives the task type from those two toggles.
- **Custom schema renderer:** Implemented a small renderer (`components/composer/schema-params-form.tsx`) instead of `react-jsonschema-form`, supporting enum, integer, number, boolean, and string plus `minimum`/`maximum`/`minLength`/`maxLength`. Unsupported shapes fall back to a text input and pass through unchanged.
- **Native validation disabled:** The form uses `noValidate` so the browser's constraint UI (e.g. the `max` bubble on number inputs) cannot pre-empt submission; `lib/generation-params.ts` validates and maps messages to the offending field instead.
- **Numeric inputs:** Number fields hold raw strings while typing and are coerced at submit time, so partial values like `-` or `0.` don't get swallowed. Blank values are omitted so server defaults apply.
- **Idempotency key ownership:** The composer generates one key per distinct payload signature (`JSON.stringify` of the submit body), reuses it when retrying an unchanged submission, and clears it after success. Changing any field produces a new key.
- **Error surfacing:** `402` shows a credits message, `429` includes `Retry-After`, `MISSING_INPUT` attaches to the image picker, FastAPI `422` issue lists map to matching schema fields when possible, and everything else falls back to the problem `detail`.

### T6.5 — Job status/history notes and assumptions
- **Realtime + fallback:** `hooks/use-job-realtime.ts` subscribes to `postgres_changes` on `generation_jobs` filtered by project. If the channel is not `SUBSCRIBED` within 5s, errors, or closes, the UI switches to polling. The timeout is overridable (`realtimeTimeoutMs`) so tests don't wait 5 seconds.
- **Polling scope:** Detail polling (`useLiveJob`) runs only for active jobs and only while the Realtime state is `disconnected`; with a live channel it stays disabled so the cache patch is the single source of truth. Backoff is 2s × 1.5ⁿ capped at 10s. A terminal polled status invalidates the list so outputs are fetched once.
- **Cache patching:** Realtime UPDATE payloads only carry row fields, not outputs, so updates patch every cached list under `["generations", projectId]` plus `["generation", id]`, then invalidate on terminal status to pick up outputs and derived fields.
- **"Use as input" adapter:** Outputs are not full asset records. `outputToAsset` builds a lightweight `Asset` from the output (`asset_id`, kind, mime, signed URL, source job) with empty workspace/project/storage fields, which is enough for the composer's image picker and submit payload. It is only offered for image outputs.
- **Composer remount:** The project page stores the chosen asset as `seedAsset` and remounts the composer with `key={seedAsset?.id ?? "composer"}` so the initial asset is applied without adding effect-driven state syncing.
- **E2E without Realtime:** The Playwright mock backend has no Realtime server, so `e2e/generation.spec.ts` deliberately exercises the polling fallback by advancing job state in `GET /v1/generations/{id}` (queued → running → succeeded) and asserting the card reaches `succeeded` and shows the output without a reload.

### T7.1 - Rate limits, quotas, and abuse-control notes
- **Token bucket:** `api/rate_limit.py` runs a Lua script (`HMGET`/`HSET`/`EXPIRE`) so the read-refill-consume-write cycle is atomic across API workers. Each bucket stores `tokens` and the last refill timestamp in Redis; capacity equals the per-minute allowance, so the configured value is also the burst size. Keys expire after one full refill window plus 60 seconds.
- **Two scopes:** Submit and retry share `ratelimit:submit:{user|workspace}:<id>`; uploads use `ratelimit:upload:...`. Both the caller's personal bucket and the workspace bucket are consumed, so one member cannot spend the whole workspace budget and a shared workspace still caps aggregate throughput. Retries are charged to the submit budget.
- **Fail-open:** If `redis_pool` is `None`, Redis `eval` raises, or the reply is unexpected, the request is allowed and a warning is logged. This keeps local development and transient Redis outages working; Cloudflare edge rules are the backstop documented in `docs/runbooks/cloudflare.md`.
- **Dependency wiring:** The limiter runs as a FastAPI route dependency on `POST /projects/{id}/generations`, `POST /generations/{id}/retry`, and `POST /projects/{id}/assets/uploads`. It resolves the workspace from the project/job row before consuming the workspace bucket. A `429` uses the existing problem+json shape with `error_code=RATE_LIMITED` and a `Retry-After` header in whole seconds.
- **Prompt length:** `MAX_PROMPT_CHARS` (default 4000) applies to both `prompt` and `negative_prompt`. The check runs after the idempotency replay but before model lookup, so a replayed request still returns its original job and an oversized prompt never reaches a provider or the ledger. Violations raise `PromptTooLongError` (`PROMPT_TOO_LONG`, 422).
- **Moderation:** `ModerationService.check(prompt, input_asset_ids)` defaults to a no-op; `StaticModerationService` is provided for tests/dev. The API resolves an app-scoped implementation from `app.state.moderation_service`, and `GenerationService` calls it before model loading and credit reservation. A rejection raises `ContentRejectedError` (`CONTENT_REJECTED`, 422) and therefore never reserves or refunds credits.
- **Concurrency cap:** The existing `MAX_ACTIVE_JOBS_PER_WORKSPACE` check in `GenerationService` remains the per-workspace job cap; it is now documented alongside the new limits in `.env.example`.

### T7.2 - Observability notes
- **Optional Sentry:** `studio_core.observability` imports `sentry_sdk` lazily and treats a missing SDK or empty `SENTRY_DSN` as a no-op. API, worker, and web therefore run normally in local development and tests without a Sentry account. The web app reads `NEXT_PUBLIC_SENTRY_DSN` at runtime and initialises from the `SentryInit` client component in the root layout.
- **Release tagging:** `get_release()` prefers `SENTRY_RELEASE`, then `GIT_SHA`, `RENDER_GIT_COMMIT`, and `VERCEL_GIT_COMMIT_SHA`. The web build passes `NEXT_PUBLIC_SENTRY_RELEASE` explicitly. Source-map upload is deferred to T7.4 because `next.config.mjs` is not wrapped in `withSentryConfig`; the runbook calls this out.
- **API context:** The request-ID middleware sets `request.state.request_id`; `auth.py` sets `request.state.user_id` after JWT verification. The 500 handler reports the exception with request ID, path, method, and user ID. 4xx responses are not sent to Sentry.
- **Worker context:** `set_current_job_context` stores `job_id`, `provider`, `model`, and `status` in a `ContextVar` so concurrent ARQ tasks do not share context. Provider/download failures call `capture_exception` with those tags, and every `JobStateMachine.transition` emits one structured `job_transition` log line with `duration_ms` since `queued_at`.
- **Admin stats:** `GET /v1/admin/stats` is gated by the comma-separated `ADMIN_USER_IDS` allow-list (empty denies everyone). It returns queue depth/oldest age, a 15-minute failure rate, 24-hour time-in-state and duration averages, and per-provider job/error/latency/cost aggregates. Queries are parameter-free (no user input) and read directly from Postgres.
- **Staging verification:** T7.2's `Verify` step requires staging, which is provisioned in T7.3. Locally the behaviour is proven by `apps/api/tests/test_t72_observability.py`, `apps/worker/tests/test_t72_observability.py`, and `apps/web/src/test/sentry.test.ts`, and the exact forced-error procedure for each service is documented in `docs/runbooks/observability.md`.
- **`.gitignore` repair:** The Python-packaging rule `lib/` was also ignoring `apps/web/src/lib/`, so the web `api.ts`, Supabase clients, and utils were never committed even though the app imports them. Added `!apps/web/src/lib/` and committed the directory alongside `sentry.ts`; a fresh checkout can now build the web app.

### T7.4 - CD pipeline notes
- **Workflow shape:** `.github/workflows/deploy.yml` runs on `pull_request` (preview), `push` to `main` (staging), and `workflow_dispatch` with a `target` choice. The `production` job declares `environment: production`, so required reviewers configured in GitHub block it until approved. The staging path is migrations → Render deploy hooks (API + worker) → Vercel deploy hook → `/readyz` wait → smoke test with a real generation.
- **Optional preview infrastructure:** Supabase branching and Vercel CLI previews are opt-in via the `SUPABASE_BRANCHING_ENABLED` and `VERCEL_PREVIEWS_VIA_CLI` repository variables. Vercel's Git integration already creates PR previews, so enabling the CLI path without disabling the integration would duplicate deployments.
- **Smoke authentication:** The workflow obtains a fresh Supabase access token with a password grant (`STAGING_SMOKE_USER_EMAIL` / `STAGING_SMOKE_USER_PASSWORD`) instead of storing a short-lived token. The smoke user must be a workspace editor and the configured project must belong to that workspace.
- **Secrets/vars:** All credentials come from `${{ secrets.* }}`; environment URLs and model slugs come from `${{ vars.* }}`. The full list is in `docs/runbooks/deployment.md`. No service-role key is used by the web or smoke steps.
- **Migration policy:** Documented in the runbook as expand → migrate → contract, with migrations always run from CI against the direct connection.
- **Local verification:** `tests/infra/test_t74_cd.py` asserts the triggers, job ordering, protected production environment, secret usage, and migration-policy documentation; the workflow parses with PyYAML and passes ruff/mypy.
- **Staging limitation:** There is no GitHub remote and no Render/Vercel/Supabase account in this environment, so the DoD's live merge-to-staging run and the rollback rehearsal could not be executed. The workflow, required configuration, and a step-by-step rehearsal checklist are committed; the first real merge will exercise the pipeline.

### T7.5 - Browser E2E suite notes
- **Target:** The suite runs against the local Next.js app plus the in-process mock backend (`apps/web/e2e/mock-backend.mjs`) and the FakeProvider-shaped responses it returns. No staging or preview URL is available in this environment, so the DoD's "in CI" requirement is met by the new `e2e` job in `.github/workflows/ci.yml`; the same command runs locally.
- **Coverage map:** `full-flow.spec.ts` covers magic-link sign-up, project creation, image-to-video from a library asset, canceling a running job, retrying a `FAIL` prompt, and the `NO_CREDITS` path. `upload.spec.ts` covers image upload, `generation.spec.ts` covers text-to-image with the polling fallback, and `a11y.spec.ts` covers axe scans, focus traps, the 375px layout, and the dark theme. Together they cover every step in the task's flow.
- **State isolation:** The mock server lives for the whole Playwright process, so `POST /__test__/reset` restores the seeded project/asset and clears jobs before each test (`helpers.ts`). Without it, jobs from one test would leak into the next.
- **Failure and credit modes:** Prompts containing `FAIL` transition to `failed` with a simulated provider error; `CANCEL`/`SLOW` stay running so cancel can be exercised; `NO_CREDITS` returns the 402 problem+json shape and the UI asserts that no job was created. Retry creates a new job from the failed one.
- **Production-mode CI:** `e2e/dev-server.mjs` starts `next dev` by default and `next start` when `E2E_USE_PROD=1`. CI builds `@studio/api-client` and `@studio/web` first, then runs the suite, which avoids the multi-minute on-demand compilation of a cold dev server. Locally the same path is `E2E_USE_PROD=1 pnpm --filter @studio/web e2e` after a build.
- **Artifacts:** `playwright.config.ts` keeps traces and videos on failure, screenshots only on failure, and the CI reporter emits HTML as well as the list output. The workflow uploads `apps/web/test-results` and `apps/web/playwright-report` when the job fails, with 7-day retention.
- **Timing:** The production-mode suite runs 15 tests in about 1.5 minutes on this machine; the warm dev-mode suite took about 5.6 minutes, and a cold dev run exceeded the 8-minute budget. The CI job has a 15-minute timeout.
- **Flake measurement:** 20 consecutive production-mode repeats (300 tests) passed with zero failures in 23.7 minutes, i.e. 0% flake against the < 2% target.
- **Static guards:** `tests/infra/test_t75_e2e.py` asserts the failure-artifact settings, the CI job's build/run/upload steps and `E2E_USE_PROD`, the production-server switch, and the presence of each launch-flow marker in the specs.
- **Limitation:** Because no preview/staging deployment exists yet, the suite was not run against a deployed environment. When T7.3/T7.4 infrastructure is available, pointing Playwright's `baseURL` at the preview is the remaining integration step; the mock is intentionally self-contained so CI does not depend on external services.
